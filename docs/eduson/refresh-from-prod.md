# Обновление локальной базы из прода старой системы

Пока платформа перерабатывается, источник правды — прод старой системы Eduson
(Express + node:sqlite в Docker). Локальная база `eduson` не дополняется, а **целиком
пересобирается** из свежего снимка прода: миграции → `import_eduson` → подмена.

Скрипт — `scripts/refresh_from_prod.sh` (bash, Git Bash на Windows), расписание —
`scripts/register_refresh_task.ps1` (Планировщик Windows, ежедневно 06:30).

## ⚠ Что затирается

**Всё, что введено в локальной платформе.** Обновление ничего не сохраняет: новая база
строится с нуля из снимка прода. Пропадают уроки, оплаты, комментарии, учётки, 2FA,
настройки, правки групп и направлений — всё, чего нет в старой системе. Остаётся
только то, что пришло с прода, плюс сиды миграций (воронка продлений, доска задач,
настройки по умолчанию).

Предыдущее состояние живёт одну итерацию в `eduson_prev` (см. «Откат»), следующий
успешный запуск его удаляет. Нужно что-то сохранить надолго — снимите `pg_dump`
вручную до запуска.

Решения владельца, которые импорт закрепляет при каждой пересборке (2026-10-19):
длина курса группы (`lessons_total`) не берётся из `package_size` Eduson — она из
направления; направления «Группа» нет, групповые группы курса `groups` разносятся
по первой букве кода (П → Python, С → Scratch, В → Вайб-кодинг).

Уроки до запуска старой системы, которых нет в её базе, импорт берёт из публичных
Google-таблиц Eduson (вкладки «Июнь 2026» и «Июнь 2027»), но только для групп, у
которых после правил базы осталось «пройдено до учёта» N > 0 (см. «Таблицы Eduson»).

## Как работает

1. **Снимок на проде — только чтение.** Внутри контейнера `node -e` открывает боевую
   SQLite через `node:sqlite` с `readOnly: true` и делает `VACUUM INTO` во временный
   файл `/tmp/okk-refresh-….db` (согласованная копия с учётом WAL). Затем `docker cp`
   на хост, удаление временного файла в контейнере, `sha256sum`. Других команд на
   сервере нет.
2. **Скачивание** `scp`, сверка sha256, `PRAGMA quick_check`, удаление временного файла
   на хосте. Временные файлы на сервере удаляются и при ошибке (trap). SSH нестабилен
   («banner exchange timeout»): каждое `ssh`/`scp` — до 5 попыток с паузой 20 с,
   `BatchMode=yes`, `ConnectTimeout=30`, соединения строго по одному.
3. **Снимок** ложится в `EDUSON_SNAPSHOT_DIR/okk-ГГГГММДД-ЧЧММ.db` (время МСК), хранятся
   последние `EDUSON_SNAPSHOT_KEEP`. Каталог обязан быть вне репозитория — это ПДн.
4. **Таблицы Eduson** (необязательно, см. ниже) — 8 CSV в `EDUSON_SNAPSHOT_DIR/sheets-ГГГГММДД-ЧЧММ/`.
5. **Сборка рядом.** Имя рабочей БД — из `DATABASE_URL` (должно начинаться с `eduson`,
   иначе отказ: защита БД KOTOKOD `journal*`; `*_test` тоже отказ). Создаётся
   `<имя>_next`, в неё `migrate` и `import_eduson <снимок> --as-of <сегодня МСК>
   [--superadmin …] [--sheets-dir …]`. Упал импорт или сверка — рабочая база **не тронута**, `_next`
   остаётся для разбора, скрипт завершается с ошибкой.
6. **Подмена.** Вход в рабочую БД закрывается, её соединения рвутся
   (`pg_terminate_backend` только для неё), старая `_prev` удаляется, рабочая
   переименовывается в `<имя>_prev`, `_next` — в `<имя>`.
7. **Итог** — размер снимка, sha256, каталог таблиц, время, таблица сверки импорта и
   строки «из таблиц». Лог —
   `EDUSON_SNAPSHOT_DIR/refresh.log` (без ПДн и секретов: ни адреса сервера, ни
   `DATABASE_URL`, ни почт).

Два запуска одновременно не пойдут: блокировка `EDUSON_SNAPSHOT_DIR/.refresh.lock`
(блокировку умершего процесса скрипт снимает сам).

## Таблицы Eduson

Четыре публичные Google-таблицы (по курсу: scratch, python, vibe, groups; доступ «по
ссылке: просмотр», без ключа API). Скрипт скачивает у каждой две вкладки — «Июнь 2026»
и «Июнь 2027» — в `sheets-<метка>/{course}-2026-06.csv` и `{course}-2027-06.csv` и
передаёт каталог в `import_eduson --sheets-dir`.

- **Правильная вкладка.** gviz-выгрузка по имени вкладки
  (`…/gviz/tq?tqx=out:csv&sheet=<имя>`) при несуществующем имени молча отдаёт первую
  вкладку. Поэтому скрипт сначала скачивает `…/htmlview`, находит в списке вкладок
  (`items.push({name: "Июнь 2027", …, gid: "…"})`) ровно одну вкладку с нужным именем и
  берёт CSV по её `gid` (`…/gviz/tq?tqx=out:csv&gid=<gid>`). Нет вкладки — отказ.
  Вторая защита: CSV двух вкладок одной таблицы не должны совпадать байт в байт.
- **Проверки ответа:** тип `text/csv`, в начале нет HTML (страница входа при закрытом
  доступе), первая ячейка шапки — «Название группы».
- **Повторы** — как у `scp`: до 5 попыток с паузой 20 с на каждую загрузку.
- **Не валит обновление.** Не задан хоть один `EDUSON_SHEET_*`, недопустимый ID, не
  скачалось или не прошло проверку — каталог удаляется, импорт идёт без `--sheets-dir`
  (как раньше: уроки до запуска остаются в «пройдено до учёта»), в лог — предупреждение.
- **Хранение.** CSV содержат ПДн (имена преподавателей и т. п.) — лежат только в
  `EDUSON_SNAPSHOT_DIR` (вне репозитория), старые каталоги удаляются вместе со снимками
  (храним `EDUSON_SNAPSHOT_KEEP`). ID таблиц — только в `.env`, в лог не пишутся.

Что импорт делает с отметками (правило — `analysis.sheet_backfill`): для группы с N > 0
берутся отметки `TRUE` раньше её первого проведённого урока и не позже дня импорта
(«Июнь 2027» — та же ошибка года, что у held «2027-06-DD», → 2026-06-DD). Отметок ≤ N —
заводятся все, N уменьшается на их число; больше N — N самых поздних, группа — в «на
ручную проверку». Уроки проведённые, посещаемость «был» всем ученикам группы, без
зарплаты, `submitted_by_token='eduson-import:sheets'`. Отметка в день незаполненного
занятия группы проводит это занятие (без второй позиции); в день отменённого — урок
заводится отдельно, отмена остаётся. В отчёте импорта и сверке —
строки «из таблиц (до запуска …)».

## Настройка

В `platform/.env` (образец и пояснения — `.env.example`, раздел «Обновление из прода»):

| Переменная | По умолчанию | Что это |
|---|---|---|
| `EDUSON_PROD_SSH` | — (обязательна) | `user@host` сервера старой системы |
| `EDUSON_PROD_CONTAINER` | `aiokk-web` | Docker-контейнер старой системы |
| `EDUSON_PROD_DB` | `/app/server/data/okk.db` | путь к SQLite внутри контейнера |
| `EDUSON_SNAPSHOT_DIR` | `../data/prod-snapshots` (от `platform/`) | каталог снимков и лога |
| `EDUSON_SNAPSHOT_KEEP` | `7` | сколько снимков хранить |
| `EDUSON_SUPERADMINS` | — | почты admin Eduson через запятую → `--superadmin` |
| `EDUSON_SHEET_SCRATCH`, `EDUSON_SHEET_PYTHON`, `EDUSON_SHEET_VIBE`, `EDUSON_SHEET_GROUPS` | — | ID Google-таблиц Eduson по курсам (`[A-Za-z0-9_-]`); не заданы — импорт без таблиц |

Также: `PSQL` (иначе `psql` из PATH, иначе `C:/Program Files/PostgreSQL/15/bin/psql`),
`PYTHON` (иначе `platform/.venv`). Нужен PostgreSQL ≥ 14 (`pg_terminate_backend`
с таймаутом). Пользователь из `DATABASE_URL` должен быть владельцем рабочей БД и
иметь право `CREATEDB`.

Перед первым запуском один раз зайдите на сервер руками (`ssh user@host`) и примите
ключ хоста: в `BatchMode` скрипт не может ответить на вопрос о неизвестном ключе.
Пользователь на сервере должен иметь право запускать `docker`.

## Запуск вручную

```bash
cd platform
bash scripts/refresh_from_prod.sh
```

После подмены **перезапустите runserver и Celery**: их соединения с базой разорваны,
а `CONN_MAX_AGE` держит соединения до минуты — перезапуск гарантирует, что процессы
работают с новой базой. Vite-серверы фронта перезапускать не нужно.

## Расписание

```powershell
# включить: ежедневно в 06:30 (пропущенный запуск — при первой возможности)
powershell -ExecutionPolicy Bypass -File scripts\register_refresh_task.ps1
# другое время
powershell -ExecutionPolicy Bypass -File scripts\register_refresh_task.ps1 -Time 05:45
# выключить
powershell -ExecutionPolicy Bypass -File scripts\register_refresh_task.ps1 -Unregister
# запустить сейчас / посмотреть результат последнего запуска
Start-ScheduledTask -TaskName EdusonRefreshFromProd
Get-ScheduledTaskInfo -TaskName EdusonRefreshFromProd
```

Задача работает от текущего пользователя, пока он вошёл в систему (нужен его
SSH-ключ), запускает `bash.exe` Git for Windows. Результат — в `refresh.log`.
runserver после ночной подмены перезапустите утром.

## Откат на предыдущую базу

`<имя>_prev` — состояние до последнего успешного обновления. Остановите runserver и
Celery, затем (подставьте свои параметры подключения):

```sql
-- подключение к служебной БД postgres
SELECT pg_terminate_backend(pid) FROM pg_stat_activity WHERE datname = 'eduson';
ALTER DATABASE eduson RENAME TO eduson_bad;
ALTER DATABASE eduson_prev RENAME TO eduson;
-- после разбора: DROP DATABASE eduson_bad;
```

Неудачная сборка оставляет `eduson_next` — её можно открыть и разобрать; следующий
запуск удалит её сам. Ошибка подмены откатывается скриптом: рабочая база
возвращается под своё имя и снова открыта для входа.
