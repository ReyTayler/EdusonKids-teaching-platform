# Планирование занятий — материализованные плановые уроки

> Спека модели `PlannedLesson` и операций расписания. Источник правды по датам
> плановых занятий — таблица `planned_lessons` (materialize-on-write). Заменяет
> прежнюю вычисляемую модель (compute-on-read из слотов + `lesson_schedule_exceptions`).

## Зачем материализация

Онлайн-школе нужно недельное расписание группы/индива, развёрнутое от даты старта,
с операциями: разовый перенос даты, смена преподавателя (разово/навсегда), изменение
расписания (чистая перегенерация хвоста от даты), отмена (перенос в конец курса +
перенумерация, курс продлевается), доп. занятие. Дата-двигающие операции и смена
препода разведены.
Материализованные строки —
источник правды — лучше ложатся на roadmap платформы (видео-комнаты, напоминания,
тема на конкретный урок, FK план→факт) и на семантику отмены-со-сдвигом, которую
compute-on-read выражал плохо.

**Ключевое отличие семантики отмены от прежней:** отмена **не** списывает урок с
абонемента и **не** укорачивает курс — N уроков сохраняются, курс заканчивается
позже. Отмена ставит маркер на дату и **переносит отменённую строку в конец
курса** (на первый свободный слот после последнего курсового занятия), после
чего все pending/overdue курсовые строки **перенумеровываются подряд по дате**.
Несколько отмен → курс продлевается ровно на число отмен, **без пустых недель**,
независимо от порядка. Прежний код относил (в порядке смены) «отмена на месте,
курс короче», слепой сдвиг `+7` и непрерывный relay всего хвоста — все три
заменены моделью «перенос в конец + перенумерация» (2026-07-21).

**Общие примитивы (максимум переиспользования).** Поверх `planner.py` (чистые
функции, без ORM) и `repository.py` (запись в БД):

- `planner.generate(..., start_seq=1, start_number=0)` — разворачивает план (или
  хвост, если `start_seq>1`) от даты по слотам; используется и «Задать
  расписание» (полный план), и «Изменить расписание» (хвост от новой даты).
- `planner.renumber_by_date(rows, *, start_seq, start_number, step)` —
  переприсваивает `seq`/`lesson_number` непрерывно по возрастанию
  `(scheduled_date, scheduled_time)`. Используется отменой.
- `repository.wipe_one_offs(group_id, *, date_from, date_to=None, from_seq=None)` —
  сбрасывает разовые операции (маркеры отмен, переносы, замены) в диапазоне —
  «чистый лист» перед перегенерацией. Используется «Изменить расписание».
- `repository.preview_affected(...)` — read-only зеркало `wipe_one_offs`: список
  разовых операций, которые будут сброшены, для превью-модалки перед
  подтверждением («Изменить расписание»).

`planner.relay_from_date(..., skip_dates=...)` (непрерывная раскладка по открытому
слоту, обходя занятые даты) сейчас боевых вызывающих НЕ имеет: его единственным
потребителем была заморозка ученика, а она расписание больше не двигает (спека
2026-07-25). Функция и её тесты оставлены намеренно — примитив нужен утверждённой,
но ещё не реализованной переработке планировщика (отмена через непрерывный relay
вместо «+7»), см. `docs/superpowers/specs/` по scheduling-relay.

|----------|---------------------|

| `occurrences.py` (`_walk`/`_step_for`/`_offset_from_monday`) | переиспользуется как **чистый генератор строк** (expand-on-write), а не compute-on-read. |

## Инвариант: плановая дата проведённого занятия = фактическая

Курсовая позиция, за которой закреплён факт (`fact_lesson_id` не пуст), обязана
стоять на дате этого занятия. Поддерживается `repository.sync_position_date` и
вызовами из четырёх точек, где меняется связка позиция↔факт или дата факта:
`attach_fact` (запись урока), `link_facts` (пакетная привязка), `relink_fact`
(смена номера), `services.update_lesson` (правка даты). Разовый перенос
(`moved_from_date`) при этом гасится — метка описывала плановое движение, а дата
приходит от факта.

Прежде плановая и фактическая дата «законно расходились», и это ломало группы:
после правки дат уроков позиции оставались на старых датах, занятие висело в
календаре не в свой день, а «перенос навсегда» клал хвост курса поверх
проведённых занятий (ПИ337, ПИ314, РИ283 — август 2026).

Спека: `docs/superpowers/specs/2026-08-05-plan-health-design.md`.

## Модель `PlannedLesson`

Таблица `planned_lessons`, `managed=True` поверх настоящей Django-миграции
(`apps/scheduling/migrations/0001_*`). App `scheduling` — логичное место (сейчас без моделей).

Конвенции проекта: half-lesson `lesson_number = seq * step` (45мин → step 0.5),
даты — чистый `DateField`/`TimeField` без TZ, «сейчас» по МСК (`msk_now()`).

| Поле | Тип | Заметки |
|------|-----|---------|
| `id` | AutoField PK | |
| `group` | FK → `groups.Group` | CASCADE, `db_column='group_id'`, `related_name='planned_lessons'` |
| `seq` | Integer, nullable | порядковый номер урока в курсе (1..N); `NULL` для `extra`/маркеров отмены |
| `lesson_number` | Decimal(5,1), nullable | `seq * step` (half-lesson); `NULL` для не-курсовых строк |
| `scheduled_date` | DateField | дата занятия |
| `scheduled_time` | TimeField | время начала |
| `teacher` | FK → `teachers.Teacher` | DO_NOTHING, nullable, `db_column='teacher_id'`. **Преподаватель контента** (штатный/«перенос навсегда»). По умолчанию = учитель группы; **едет** с уроком при перекладке. |
| `substitute_teacher` | FK → `teachers.Teacher` | DO_NOTHING, nullable, `db_column='substitute_teacher_id'`. **Разовая замена на дату** (`change-teacher`). **Не едет** с контентом: обнуляется при смене `scheduled_date` строки. Эффективный преподаватель = `substitute_teacher ?? teacher` — **источник правды для скоупа календаря**. |
| `status` | TextField | `pending / overdue / done / cancelled` (константы из `occurrences.py`). `moved` — **зарезервирован в CheckConstraint, но не используется** операциями (перенос показывается через `moved_from_date`) |
| `fact_lesson` | FK → `lessons.Lesson` | SET NULL, nullable, **unique**, `db_column='fact_lesson_id'` — связь план→факт |
| `moved_from_date` | DateField, nullable | отображение разового переноса (откуда); ставится только при реальной смене даты |
| `moved_to_date` | DateField, nullable | **зарезервировано, не используется** (не пишется и не отдаётся в API) |
| `note` | TextField, nullable | |
| `created_at` / `updated_at` | DateTimeField (timestamptz) | DB-default `now()` |

### Ограничения / индексы

- `UniqueConstraint(group, seq)` где `seq IS NOT NULL` — одна строка на позицию курса.
- `Index(group, scheduled_date)` — основной для календаря.
- `CheckConstraint status IN ('pending','overdue','done','cancelled','moved')`.
- `CheckConstraint`: у курсовых строк (`seq IS NOT NULL`) `lesson_number IS NOT NULL`;
  у не-курсовых (`seq IS NULL`) `lesson_number IS NULL`. (Оба заданы ⟺ оба NULL.)

## Операции (чистые функции над датами, TDD)

Файл `apps/scheduling/planner.py` — чистые функции (без ORM), тестируемые в изоляции;
`apps/scheduling/repository.py` — запись результата в БД в транзакции.

**Инвариант всех операций:** никогда не трогать строки `status='done'` (проведённые).
Операции затрагивают только будущие/непроведённые. `seq`/`lesson_number` (порядок
контента) стабильны — двигаются только даты (и опц. `teacher`).

### 1. Генерация плана `generate`

Вход: `start_date`, слоты (активные), `direction.total_lessons` (**обязателен**;
если NULL → группа «unscheduled», план не строим), `duration_minutes` (для step).
Разворачиваем N строк `seq 1..N` еженедельно на день/время слота (переиспользуем
`_walk`). Дефолт `teacher` = учитель группы. **Идемпотентно** — повторный вызов не
плодит дубли (guard по `UniqueConstraint(group, seq)`; не перезаписывает `done`).
Ручной эндпоинт `/plan/generate` и авто-генерация используют `create_only=True`
(не затирают ручные операции).

**Авто-генерация при первичной настройке (Механизм 1).** Когда у активной группы
ВПЕРВЫЕ появляются старт И слот И `total_lessons`, план генерируется автоматически —
`groups.services.{create_group,update_group,apply_schedule_change}` синхронно зовут
`scheduling.services.autogenerate_plan_on_setup(...)` ПОСЛЕ коммита repository
(`ATOMIC_REQUESTS=False` → выход из repository-atomic = commit; сигналы не годятся —
слоты создаются `bulk_create`, `post_save` не летит). Срабатывает **только первый
раз** (guard `plan_exists(active_only=True)`: непустой план / неактивная группа →
выход); идемпотентно; аудит `plan_auto_generate` (source/written/reason); гонка двух
триггеров глушится на `IntegrityError`; сбой авто-генерации не роняет создание группы.

Дата-двигающие операции (перенос) и смена преподавателя **разведены**: перенос не
переназначает препода «побочно», смена препода не двигает дату. Это устраняет
ложную метку «перенесён» при обычной смене учителя.

### 2. Разовый перенос `reschedule`

Обновить **одну** строку (по `id` планового занятия): `scheduled_date/time` и
**опц. `teacher`** (напр. подмена на этот перенос). `moved_from_date` = прежняя дата,
но **только если дата реально изменилась** (перенос на ту же дату — напр. правка
одного времени — метку «перенесён» не ставит). Остальные строки не трогаются;
`seq`/`lesson_number` сохраняются. `done` не переносим (ошибка → 409).

### 3. Смена преподавателя `change_teacher` / `change_teacher_permanent`

Отдельные операции — **не** двигают дату/время и **не** ставят `moved_from_date`.
- **Разово** (`POST /plan/<lid>/change-teacher`): пишет `substitute_teacher_id` одной
  строки — это **замена на конкретную дату**, а не преподаватель контента (`teacher_id`
  не трогается). `done` → 409. Замена — свойство КАЛЕНДАРНОЙ ДАТЫ: при любом переезде
  строки (отмена/перекладка) `substitute_teacher_id` обнуляется, т.е. замена
  «не едет» с контентом и исчезает вместе с отменённой датой.
- **Навсегда** (`POST /plan/change-teacher-permanent`): проставляет `teacher` (контент)
  всем курсовым строкам `seq >= from_seq` в статусе `pending/overdue`. Это преподаватель
  контента — он **едет** с уроком при перекладке. Слот/день не версионируются.

**Эффективный преподаватель занятия** = `substitute_teacher_id ?? teacher_id`. Календарь
скоупится по эффективному преподавателю (замена показывается в календаре подменяющего
только на её дату); admin-план тоже показывает эффективного. Контракт occurrence
(`teacher`/`teacherOverride`) сохранён по форме.

### 4. Изменить расписание `permanent_change`

Единый путь (одно/мультислотовое ветвление убрано): с позиции `seq=k` — **чистая
перегенерация хвоста** от клиентской даты `effective_from` по целевому набору
`new_slots` (1..N слотов `{day_of_week, start_time}`), в одной транзакции
(`repository.permanent_change`):
1. `wipe_one_offs(date_from=effective_from, from_seq=k)` — сбросить разовые
   переносы/замены/маркеры отмен в хвосте («чистый лист»).
2. Версионировать **весь** набор слотов от `effective_from`
   (`groups.apply_schedule_change`: закрыть старые открытые слоты, открыть новые).
3. `planner.generate(start_date=effective_from, start_seq=k, ...)` — развернуть
   остаток курса (`N − (k−1)` строк) от новой даты по новым слотам; результат
   мапится на существующие строки хвоста по `seq`.
4. `lessons_per_week = len(new_slots)`; преподаватель группы — если передан
   `new_teacher_id`.

`effective_from` — **обязательное** поле от клиента (не выводится сервером).
Голова (`seq < k`) и `done` не трогаются. Работает для любого числа слотов
(включая расширение 1→N) — прежнее ограничение «только один открытый слот»
снято.

**Превью перед применением.** `POST .../plan/permanent-change` с `preview: true`
(полное тело + флаг) возвращает `{"affected": [...]}` — список того, что
`wipe_one_offs` сбросит (`preview_affected`), **без записи**. UI показывает
диалог-предупреждение и просит подтверждения, только если список непуст.

### 5. Отмена — перенос в конец курса `cancel`

По `id` курсовой строки (`seq=k`, дата D), в одной транзакции (`repository.cancel_lesson`):
1. Вставляем маркер `status='cancelled', seq=NULL` на дату D («отменён» в
   календаре), с временем/преподавателем отменённого занятия.
2. **Переносим саму отменённую строку** на первый свободный слот-день **строго
   после** текущей последней курсовой даты группы — она становится новым
   последним занятием курса. `substitute_teacher_id`/`moved_from_date`
   сбрасываются (разовая замена/перенос — свойство даты, не едет с содержимым).
3. **Перенумеровываем** все pending/overdue курсовые строки подряд по
   возрастанию `(scheduled_date, scheduled_time)` (`planner.renumber_by_date`,
   двухфазно — временные отрицательные `seq`, затем финальные, иначе падает
   `UniqueConstraint(group, seq)`), продолжая нумерацию от последней `done`
   строки. Остальные строки **сохраняют свои даты** — сдвигается только
   позиция (`seq`), никакого relay всего хвоста.

**Неподвижны:** маркеры отмены и доп. занятия (`seq=NULL`) и проведённые (`done`).
Абонемент **не** трогаем (balance = purchased − attended; отменённый не attended).
Курс продлевается ровно на число отмен, курсовых строк всегда ровно N, без дыр,
независимо от порядка отмен. Отмена доступна только для активной курсовой строки
(не extra/cancelled/done → 400). Нет открытого слота → шаг переноса пропускается
(строка остаётся на месте), перенумерация всё равно проходит.

### 6. Доп. занятие `extra`

Вставить строку `seq=NULL, lesson_number=NULL` на заданную дату/время с преподавателем.
Вне курса, не влияет на `seq` курсовых строк. При отмене не сдвигается.

## Скоуп календаря по преподавателю

`GET /api/calendar` скоупит **по `planned_lesson.teacher_id`** (не по учителю группы).
Следствие смены преподавателя занятия (разово или навсегда): занятие автоматически
**появляется** у нового препода и **исчезает** у исходного. Дефолт `teacher` строки
= учитель группы; операции переопределяют пер-строчно. Связка с payroll/подменой
(`Lesson.original_teacher`) — на этапе факта, вне планового слоя, через `fact_lesson`.

- `POST /api/admin/groups/<pk>/plan/<lid>/cancel` — отмена (перенос в конец курса + перенумерация).
- `POST /api/admin/groups/<pk>/plan/extra` — доп. занятие.

а не восстановление прежней.

`generate` идемпотентен и **create-only** над непустым планом (не затирает ручные

## Бэкфилл (пересборка из фактов — Механизм 2)

Management-команда `apps/scheduling/management/commands/backfill_planned_lessons.py`
для активных групп со стартом+`total_lessons`+слотами пересобирает план чистой
функцией `planner.generate_from_facts` (обёртка `repository.rebuild_from_facts`):

1. **ПРОШЛОЕ = факты.** i-й факт (сорт по `lesson_date,id`) → строка `seq i`,
   `status=done`, **`scheduled_date = fact.lesson_date`** (плановая дата =
   фактическая), номер по порядку (кумулятивный `step`), `teacher`/`fact_lesson_id`
   из факта. Связь план→факт ставится напрямую (без эвристики `link_facts`). Фактов
   больше `total` → все сохраняются как done, будущего нет.
2. **БУДУЩЕЕ.** Оставшиеся уроки (`total − проведено`, в единицах с учётом
   half-lesson) разворачиваются по **текущему открытому** слоту, начиная с
   ближайшего слот-дня **строго после даты последнего проведённого урока** (а не от
   «сегодня»): план продолжается непрерывно с места, где группа остановилась.
   Пример: последний (27-й) урок в СБ `04.07` → 28-й в СБ `11.07`, 29-й `18.07`, …
   Если фактов нет — будущее от `group_start_date`. Номера/`seq` продолжают прошлое.

Непроведённые будущие строки, чья дата уже прошла (группа отстаёт от графика),
читаются как **overdue** «надо заполнить» на уровне `_planned_status` — отдельного
«overdue-прошлого» не материализуем.

**⚠️ Разрушительно и re-runnable:** каждая пересборка = `reset_plan` + `bulk_create`,
разворачивает будущее заново → **перезаписывает ручные операции будущего**
(переносы/отмены/смену препода); команда об этом предупреждает. **Результат
today-независим:** даты зависят от ФАКТОВ, а не от даты прогона — повтор без новых
фактов даёт тот же план. Батч без N+1 (`active_groups`+`slots_by_group`+
`facts_by_group`). `--dry-run` — без записи; `--reset` устарел (reset встроен) →
no-op с предупреждением. Гонять на dev-БД (`journal`, не `journal_test`).
